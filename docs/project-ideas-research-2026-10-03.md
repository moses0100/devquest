# Research: โปรเจกต์ฝึก Vibe Coding ที่มีหน้าที่ชัดเจน

วันที่ค้นคว้า: 3 ตุลาคม 2026

## สิ่งที่พบและคำแนะนำ

ควรเลือกโปรเจกต์จากงานที่ผู้ใช้ต้องทำให้เสร็จ มากกว่าจากรายชื่อฟีเจอร์หรือความแปลกของชื่อแอป สำหรับเป้าหมายของผู้ใช้ที่ต้องการฝึก Vibe Coding, Tech Stack ใหม่ และ GitHub มีสามแนวที่ควรทดลองก่อน:

1. **Repo Passport** — ช่วยคนเริ่มเขียนโค้ดรู้ว่าโปรเจกต์นี้ต้องใช้อะไร และติดตรงไหนก่อนรัน เหมาะกับเป้าหมายที่ทราบจากบทสนทนามากที่สุด
2. **ChangeLens** — เปรียบเทียบไฟล์ตารางแล้วอธิบายสิ่งที่เปลี่ยนเป็นภาษาคน เหมาะหากมีงาน Excel/CSV จริงให้ใช้
3. **Thai PDF Rescue** — ตรวจและแก้ปัญหาดึงข้อความไทยจาก PDF เฉพาะรูปแบบที่รองรับ เหมาะหากอยากทำเครื่องมือเฉพาะทางและหาเอกสารทดสอบได้

นี่คือคำแนะนำจากการวิเคราะห์ ไม่ใช่ผลทดสอบว่าผู้ใช้รายนี้จะชอบหรือมีคนยอมจ่าย ยังไม่มีการสัมภาษณ์ ทดลองขาย หรือทดสอบผลิตภัณฑ์คู่แข่งด้วยตนเอง

## วิธีค้นคว้าและข้อจำกัด

- ค้นกระทู้ปัญหาจาก Reddit และ Pantip เพื่อหาเหตุการณ์ใช้งาน ไม่ใช้ยอดโหวตแทนขนาดตลาด
- ตรวจเว็บไซต์ เอกสาร และ repository ของเครื่องมือที่มีอยู่ เพื่อตัดไอเดียที่ซ้ำความสามารถทั่วไป
- ใช้เอกสารต้นทางสำหรับข้อเท็จจริงทางเทคนิค
- ข้อเสนอว่าจะแตกต่างอย่างไรเป็นสมมติฐานของผู้จัดทำ ไม่ใช่ข้อพิสูจน์ว่าไม่มีคู่แข่งทำสิ่งนั้น
- กระทู้บางส่วนเป็นโพสต์โปรโมตหรืออาจมีผลประโยชน์แฝง จึงไม่ใช้คำกล่าวเรื่องเปอร์เซ็นต์ตลาด รายได้ หรือความนิยมโดยไม่มีการตรวจสอบเพิ่มเติม
- เอกสารผลิตภัณฑ์บอกความสามารถที่ผู้ผลิตระบุ ไม่ได้พิสูจน์คุณภาพ ความเร็ว ความแม่นยำ หรือความง่ายของการใช้
- การค้นครั้งนี้ไม่ใช่การสำรวจตลาดครบทุกประเทศ และไม่สามารถรับรองความใหม่ระดับโลก

## 1. Repo Passport: โปรเจกต์นี้ต้องใช้อะไรถึงจะรันได้

### เหตุการณ์ใช้งาน

ผู้เริ่มต้นได้รับโค้ดจาก AI หรือ clone จาก GitHub แล้วพบว่าไม่รู้ว่าต้องติดตั้งอะไร ต้องเปิดฐานข้อมูลไหม และ `.env` ต้องใส่อะไร หน้าแรกของเครื่องมือควรให้เลือกโฟลเดอร์หรือ ZIP แล้วอธิบายสิ่งที่พบด้วยภาษาไทย

ตัวอย่างผลลัพธ์ที่เราตั้งใจทำ:

- พบโปรเจกต์ Node.js และคำสั่ง `dev` ใน package.json
- พบตัวแปร DATABASE_URL ในโค้ด แต่ไม่พบคำอธิบายใน .env.example
- พบ Docker Compose ที่ประกาศ PostgreSQL
- พบ lockfile สองชนิด จึงให้ผู้ใช้เลือก package manager
- ยังไม่ได้รันโค้ด จึงยืนยันไม่ได้ว่าหน้าเว็บหรือ API ใช้งานสำเร็จ

### สิ่งที่มีอยู่แล้ว

[GitHub Dev Containers](https://docs.github.com/en/codespaces/setting-up-your-project-for-codespaces/adding-a-dev-container-configuration/introduction-to-dev-containers) ใช้กำหนดสภาพแวดล้อมพัฒนา และ [mise project diagnostics](https://mise.jdx.dev/configuration/project-diagnostics.html) มีการตรวจตามคำสั่งที่ประกาศไว้แล้ว จึงไม่ควรเสนอว่า environment management หรือ project doctor เป็นสิ่งใหม่

**สมมติฐานจุดต่าง:** ตรวจ repository ที่ยังไม่ได้เตรียม configuration ให้ดี แล้วทำรายงานสำหรับมือใหม่ รวมถึงอธิบายสิ่งที่ไม่สามารถอนุมานได้ โดยไม่ต้องให้ผู้ใช้รู้จักเครื่องมือเหล่านั้นก่อน

### เวอร์ชันแรก

1. อ่าน package.json, lockfile, .env.example, README และ Compose จากโฟลเดอร์ที่ผู้ใช้เลือก
2. ดึงเฉพาะชื่อตัวแปร ไม่ส่งค่าจาก .env ไปเซิร์ฟเวอร์
3. แสดงข้อเท็จจริงที่พบและรายการที่น่าจะขาด พร้อมลิงก์ไปไฟล์ต้นทาง
4. ส่งออกรายงาน Markdown และร่างขั้นตอนเริ่มใช้งาน

เริ่มรองรับเฉพาะ Node.js ก่อน ไม่ต้องรับ Laravel/Python/Rust ทั้งหมดในรอบแรก การสแกนข้อความไม่สามารถพบ env ที่ประกอบชื่อแบบ dynamic ได้ทุกกรณี และการอ่าน README ไม่เท่ากับพิสูจน์ว่าคำสั่งรันได้

**Stack ที่เสนอ:** TypeScript CLI ก่อน แล้วค่อยเพิ่มหน้า React หรือ desktop UI หากจำเป็น ได้ฝึก filesystem, parsing, configuration, packaging และ GitHub Actions ไม่จำเป็นต้องมีฐานข้อมูลในเวอร์ชันแรก

**สิ่งที่ยังไม่ควรทำ:** รัน npm install หรือ shell script ของ repository ที่อัปโหลดโดยอัตโนมัติ ถ้าจะเพิ่มการรันจริงภายหลังต้องออกแบบการแยกสภาพแวดล้อม การอนุญาต และขอบเขตทรัพยากรใหม่

**พิสูจน์ประโยชน์:** ใช้กับ repository ที่มีปัญหา 5 แบบ เช่นไม่มี script, ไม่มี env example, runtime ไม่ตรง, lockfile ซ้ำ และมีฐานข้อมูลที่ README ไม่กล่าวถึง ให้ผู้เริ่มต้นอธิบายขั้นตอนต่อไปจากรายงาน เทียบกับอ่าน README อย่างเดียว

**เหตุผลที่จะหยุด:** รายงานเป็นเพียงข้อความทั่วไปที่ AI เดา หรือไม่ช่วยให้ผู้เริ่มต้นระบุขั้นตอนถัดไปได้ดีขึ้น

## 2. ChangeLens: บอกว่าข้อมูลเปลี่ยนอะไร ไม่ต้องไล่ดูทุกช่อง

### เหตุการณ์ใช้งาน

ได้รับไฟล์ราคาหรือข้อมูลฉบับใหม่ แต่คอลัมน์ไม่ตรงกัน แถวถูกสลับ และต้องการรู้ว่ารายการไหนเพิ่ม หาย หรือเปลี่ยนค่า มี [กระทู้เปรียบเทียบราคาจาก supplier หลายราย](https://www.reddit.com/r/excel/comments/1gnf0a7/need_to_compare_different_suppliers_price_lists/) ที่ผู้ถามติดเรื่องรวมข้อมูลและรหัสสินค้า และต่อมาระบุว่า Power Query ช่วยแก้ปัญหาได้แล้ว นั่นเป็นทั้งหลักฐานของปัญหาและหลักฐานว่ามีวิธีแก้อยู่

### สิ่งที่มีอยู่แล้ว

[Diffchecker Excel](https://www.diffchecker.com/excel-compare/) เปรียบเทียบตารางและสูตรได้ ส่วน [Spreadsheet Compare](https://support.microsoft.com/en-us/excel/overview-of-spreadsheet-compare) เป็นเครื่องมือของ Microsoft และ [OpenRefine](https://openrefine.org/docs/manual/reconciling) มีงาน reconciliation ดังนั้นการเทียบไฟล์หรือจับคู่ข้อมูลทั่วไปไม่ใช่ความใหม่

**สมมติฐานจุดต่าง:** เน้นไฟล์งานไทยที่หัวคอลัมน์ต่างกัน และเปลี่ยนผลการเทียบเป็นรายงานที่คนทำงานอ่านได้ทันที เช่น “เพิ่มสินค้า 3 รายการ ราคาปรับ 2 รายการ รหัสซ้ำ 1 รายการ” พร้อมดูแถวต้นทางได้

### เวอร์ชันแรก

1. รับ CSV สองไฟล์ก่อน
2. ให้เลือกคอลัมน์รหัสสินค้าและคอลัมน์ที่จะเทียบ
3. จับคู่ด้วยรหัสที่ตรงกัน แสดงรหัสซ้ำแยกออกมา
4. แสดง added/removed/changed พร้อมค่าเดิมและใหม่
5. ส่งออกรายงาน CSV และสรุปภาษาไทยด้วย template

ตัวอย่างที่ใช้สาธิตได้: ไฟล์เก่า A001 ราคา 100 บาท ไฟล์ใหม่ A001 ราคา 120 บาท เครื่องมือรายงานเพิ่ม 20 บาทหรือ 20% ส่วน A002 ที่ไม่พบในไฟล์ใหม่รายงานว่า “ไม่พบในไฟล์ใหม่” ไม่สรุปเองว่าบริษัทเลิกขายแล้ว

**Stack ที่เสนอ:** TypeScript + React หรือ Svelte, ประมวลผลใน browser worker เริ่มจาก CSV จึงยังไม่ต้องมี server, account หรือฐานข้อมูล เพิ่มการอ่าน XLSX ภายหลังเมื่อมีตัวอย่างงานจริง

**จุดยาก:** รหัสมีศูนย์นำหน้า, วันที่ไทย/คริสต์ศักราช, ราคาก่อนและหลังภาษี, หน่วยขายไม่เหมือนกัน, หลายรายการใช้ชื่อคล้ายกัน การจับคู่ชื่อแบบคลุมเครือต้องเสนอให้คนยืนยัน ไม่ควรรวมสินค้าทันที ส่วนสูตร Excel ต้องแยกออกจากค่าที่แสดงและยังไม่รองรับใน MVP

**พิสูจน์ประโยชน์:** ให้คนที่ทำงานตารางใช้ไฟล์จริงที่ตัดข้อมูลส่วนตัวแล้ว ตรวจว่ารายงานตรงกับผลตรวจด้วยมือ และใช้เวลาน้อยลงหรือไม่

**เหตุผลที่จะหยุด:** งานเป้าหมายใช้ Power Query ที่ตั้งค่าไว้แล้วได้ง่ายกว่า หรือความผิดพลาดในการจับคู่ทำให้ต้องตรวจทุกแถวใหม่

## 3. Thai PDF Rescue: เปิดอ่านได้ แต่คัดลอกข้อความไม่ได้

### เหตุการณ์ใช้งาน

PDF ภาษาไทยแสดงผลถูก แต่คัดลอกแล้ววรรณยุกต์เพี้ยนหรืออักขระผิด อีกกรณีคือ PDF เป็นภาพสแกนและไม่มีข้อความเลย สองปัญหานี้ต้องแยกกัน ไม่ใช่ส่งเข้า OCR ทุกไฟล์

### สิ่งที่มีอยู่แล้ว

มี [DOCOCR ของ AI for Thai](https://docr.aiforthai.in.th/) และระบบ [Paperless-ngx](https://docs.paperless-ngx.com/setup/) ที่ใช้ OCR ส่วน [โครงการ fix-thai-pdf](https://github.com/korakot/skills/blob/main/fix-thai-pdf/SKILL.md) อธิบายปัญหา PUA และลำดับ glyph ใน PDF ไทยบางตระกูล พร้อมวิธีซ่อมและข้อจำกัด จึงมีฐานทางเทคนิคให้ศึกษาจริง แต่ไม่ใช่คำรับรองว่าจะซ่อม PDF ไทยทุกชนิด

**สมมติฐานจุดต่าง:** ให้ผู้ใช้รู้ก่อนว่าไฟล์เสียแบบไหน เลือกแนวทางที่เหมาะกับไฟล์ และดูข้อความที่ได้คู่กับต้นฉบับ พร้อมส่งออกเป็นข้อความสะอาดสำหรับค้นหาและคัดลอก

### เวอร์ชันแรก

1. ตรวจว่าไฟล์มี text layer หรือเป็นภาพ
2. ตรวจลักษณะอักขระผิดที่รองรับหนึ่งกลุ่ม
3. แสดงข้อความก่อนและหลัง พร้อมหมายเลขหน้า
4. ให้แก้ข้อความและ export TXT
5. ไฟล์ที่ไม่รองรับแจ้งเหตุผล โดยไม่เดาคำมาแทน

**Stack ที่เสนอ:** Python + FastAPI สำหรับอ่านและประมวลผล PDF, React สำหรับตรวจผล ไม่ต้องเพิ่มฐานข้อมูลจนกว่าจะต้องเก็บงานข้ามครั้ง หากใช้โค้ดจากโครงการอื่นต้องตรวจ license ก่อน

**จุดยาก:** PDF มีหลายรูปแบบ encoding, สระและวรรณยุกต์ซ้อน, การเรียงข้อความหลายคอลัมน์ และตาราง OCR ต้องมีชุดทดสอบที่อ่านแก้ด้วยคนจริง โดยตัวเลขต้องตรวจแยกอย่างเข้มงวด ไม่เริ่มด้วยการแปลง statement ทุกธนาคารหรือรับรองยอดบัญชี

**พิสูจน์ประโยชน์:** รวบรวมเอกสารที่อนุญาตให้ใช้ 10–20 ไฟล์จากหลายแหล่ง เปรียบเทียบข้อความกับต้นฉบับที่คนอ่านยืนยัน และบันทึกว่าประเภทไหนแก้ได้/ไม่ได้

**เหตุผลที่จะหยุด:** ไม่มีไฟล์ตัวอย่างจริง หรือแก้ได้เพียงตัวอย่างเดียวแต่ไม่สามารถบอกขอบเขตที่รองรับได้

## 4. BriefTrace: คำขอแก้รอบนี้เปลี่ยนอะไรจากที่ตกลงไว้

### เหตุการณ์ใช้งาน

ฟรีแลนซ์และทีมเล็กได้รับ feedback หลายรอบ ต้องย้อนหาว่าข้อไหนเป็นของเดิม ข้อไหนเพิ่ม และข้อไหนขัดกับคำขอก่อนหน้า มี [กระทู้ของฟรีแลนซ์](https://www.reddit.com/r/freelance/comments/1to9m9h/nightmare_client_from_hell_please_help/) ที่อธิบายปัญหาการเพิ่ม/เปลี่ยนคำขอและข้อความติดตามงานหลายรอบ ใช้เป็นตัวอย่างเหตุการณ์ ไม่ใช้เป็นสถิติสัดส่วนโครงการทั้งหมด

### สิ่งที่มีอยู่แล้ว

[Filestage](https://help.filestage.io/en/articles/7872784-chapter-3-managing-versions) เก็บเวอร์ชัน เปรียบเทียบงานและความคิดเห็น และส่งออกรายงานได้ ส่วน [Pastel](https://help.usepastel.com/en/articles/1996011-reviewing-websites-in-pastel) วาง feedback บนเว็บไซต์จริงได้

**สมมติฐานจุดต่าง:** ทำให้เห็นความสัมพันธ์ระหว่างคำขอแต่ละรอบกับ baseline ที่ผู้ใช้ยืนยันแล้ว โดยใช้งานภาษาไทยง่าย ๆ และเริ่มจากข้อความที่ผู้ใช้นำมาวางเอง

### เวอร์ชันแรก

1. สร้าง baseline รายการสิ่งที่จะส่งมอบ
2. เพิ่มชุดคำขอแก้เป็น revision
3. ให้คนจัดประเภทว่าเพิ่ม แก้ ยกเลิก หรือยังไม่ชัด
4. แสดง timeline และคำถามที่ต้องขอความชัดเจน
5. ส่งออกรายงานสรุปรอบการแก้

ถ้าเพิ่ม AI ให้เสนอการจับคู่พร้อมแสดงประโยคต้นทาง ไม่ตัดสินเองว่านอกสัญญาหรือควรคิดเงินเท่าไร ระบบนี้ช่วยทบทวนงาน ไม่ทำหน้าที่ตีความสิทธิทางกฎหมาย

**Stack ที่เสนอ:** Next.js + PostgreSQL สำหรับเว็บ; หากอยากเปลี่ยน stack จริงอาจใช้ SvelteKit + PostgreSQL ได้ฝึก versioning, transaction, audit history และ permissions ถ้าภายหลังมีหลายคน

**จุดยาก:** baseline ที่คลุมเครือ, ความไว้วางใจของทั้งสองฝ่าย และภาระการกรอกข้อมูล หากต้องคัดลอกทุกข้อความเองจนช้ากว่าแชต คนอาจเลิกใช้ ไม่เริ่มด้วยการอ่าน LINE อัตโนมัติ

**พิสูจน์ประโยชน์:** ใช้กับโครงการที่อนุญาตให้ดู feedback จริงหนึ่งโครงการ ตรวจว่าช่วยตอบได้เร็วขึ้นหรือไม่ว่า “ตอนนี้ตกลงอะไร และยังต้องถามอะไร”

**เหตุผลที่จะหยุด:** คนใช้ไม่ยอมย้ายข้อมูล หรือ report เพิ่มความขัดแย้งมากกว่าช่วยให้เข้าใจตรงกัน

## 5. BeforeSend: เตรียมไฟล์สำหรับส่งต่อโดยไม่เผลอเผยข้อมูล

### เหตุการณ์ใช้งาน

ต้องส่งภาพแคปหรือ PDF ให้คนอื่น แต่มีเบอร์โทร ชื่อ ที่อยู่ หรือข้อมูลที่ไม่ต้องการเผย บทบาทของเครื่องมือคือให้คนระบุข้อมูลที่ต้องปิด แล้วผลิตสำเนาใหม่พร้อม preview และผลตรวจซ้ำ

### สิ่งที่มีอยู่แล้ว

[Snipping Tool](https://support.microsoft.com/en-us/windows/apps/use-snipping-tool-to-capture-screenshots) มี text actions และ quick redact, [Adobe Acrobat](https://helpx.adobe.com/sg/acrobat/using/removing-sensitive-content-pdfs.html) มี redaction และ sanitize, [Stirling PDF](https://docs.stirlingpdf.com/Functionality/Page-Operations/redact/) รองรับการลบข้อความและการแปลงผลเป็นภาพ การวางกล่องดำทับ PDF โดยไม่ลบข้อมูลเดิมจึงไม่เพียงพอ

**สมมติฐานจุดต่าง:** workflow ภาษาไทยที่รับหลายไฟล์ ใช้รายการข้อมูลที่เจ้าของยืนยันเอง และตรวจผลก่อนส่ง ไม่อ้างว่า AI ตรวจพบข้อมูลส่วนตัวได้ครบ

### เวอร์ชันแรก

เริ่ม PNG/JPEG เท่านั้น: ให้ลากกรอบทับ, สร้าง bitmap ใหม่, ส่งออกไฟล์ใหม่โดยไม่คัดลอก metadata ต้นทาง และให้คนดูอีกครั้ง เพิ่ม OCR เป็นตัวช่วยค้นหาภายหลัง ไม่ใช้ OCR เป็นหลักฐานรับรองว่าปลอดภัยทั้งหมด

**Stack ที่เสนอ:** TypeScript + Canvas ใน browser ไม่ต้องอัปโหลดไฟล์ สำหรับ PDF ต้องออกแบบใหม่ให้ตรวจทั้ง text layer, annotations, attachments และ metadata

**จุดยาก:** พลาดเพียงจุดเดียวก็เผยข้อมูลได้ การเปลี่ยน PDF เป็นภาพยังไม่เท่ากับรับรองว่าปิดทุกสิ่งที่ต้องปิด การจัดตำแหน่งบนภาพที่ rotate หรือมี scaling ต้องทดสอบด้วย

**พิสูจน์ประโยชน์:** ใช้ชุดภาพสังเคราะห์ที่รู้ตำแหน่งข้อมูลทุกจุด ตรวจทั้งภาพผลลัพธ์ metadata และไฟล์ที่ส่งออก โดยไม่ใช้ข้อมูลอ่อนไหวจริงในรอบแรก

**เหตุผลที่จะหยุด:** ไม่สามารถอธิบายสิ่งที่ตรวจแล้วและสิ่งที่ยังไม่ตรวจ หรือผู้ใช้เข้าใจผิดว่าเครื่องมือรับรองความปลอดภัยสมบูรณ์

## 6. SavePoint: กลับไปก่อนลง mod หรือแก้ config

### เหตุการณ์ใช้งาน

ก่อนแก้ mod/config ผู้ใช้เลือกโฟลเดอร์และทำ snapshot หากเกมหรือโปรแกรมมีปัญหา สามารถดูความต่างและย้อนเฉพาะไฟล์ที่เลือกได้

### สิ่งที่มีอยู่แล้ว

[Ludusavi](https://github.com/mtkennerly/ludusavi) เป็นเครื่องมือ backup เซฟเกมอยู่แล้ว และ [Steam Support](https://help.steampowered.com/en/faqs/view/68D2-35AB-09A9-7678) อธิบายความเสี่ยงเรื่อง sync conflict จึงไม่ควรสร้าง backup เซฟทั่วไปแล้วเรียกว่าใหม่

**สมมติฐานจุดต่าง:** เก็บ snapshot ของ mod/config ที่ผู้ใช้เลือก พร้อมชื่อสถานะ เช่น “ก่อนเพิ่ม mod กราฟิก” แสดงสิ่งที่จะถูกเปลี่ยนก่อน restore และสำรองสถานะปัจจุบันอีกครั้งก่อนคืนค่า

### เวอร์ชันแรก

รองรับหนึ่งโฟลเดอร์: บันทึกสำเนา + hash + เวลา, แสดง added/removed/changed, preview ก่อน restore, เก็บ snapshot ก่อน restore ไม่แก้ Steam Cloud และไม่ restore ขณะเกมทำงาน

**Stack ที่เสนอ:** Tauri + Rust หรือ Electron + TypeScript หากต้องการลดจำนวนภาษาใหม่ เหมาะกับงาน desktop; เว็บปกติไม่ได้เฝ้าโฟลเดอร์เกมโดยอิสระเหมือนโปรแกรมที่ติดตั้ง

**จุดยาก:** โฟลเดอร์ผิด, symlink, ไฟล์ใหญ่, เกมล็อกไฟล์, เขียนไม่สำเร็จกลางทาง และ permission ต้องเริ่มทดสอบกับโฟลเดอร์จำลอง ไม่ใช้เซฟเกมจริงจน restore ผ่านการตรวจแล้ว

**พิสูจน์ประโยชน์:** สร้างโฟลเดอร์จำลอง ทำ snapshot แก้/เพิ่ม/ลบไฟล์ แล้วคืนค่า ตรวจ hash ทุกไฟล์และยืนยันว่าพื้นที่นอกโฟลเดอร์ไม่เปลี่ยน

**เหตุผลที่จะหยุด:** ความต้องการจริงเป็นเพียง backup เซฟทั่วไปที่ Ludusavi ทำได้อยู่แล้ว

## อีก 6 แนวและเหตุผลที่ยังไม่เลือกก่อน

### PC MoveKit

แผนย้ายเครื่องที่บอกว่ามีโปรแกรมอะไรและข้อมูลไหนยังไม่ได้สำรอง [winget export/import](https://learn.microsoft.com/en-us/windows/package-manager/winget/export) ช่วยเรื่องรายการโปรแกรมและติดตั้งเป็นชุดอยู่แล้ว จุดที่พอทดลองคือ manifest ของข้อมูลที่ต้องย้ายและรายงานสิ่งที่ยังขาด ไม่แอบสำรอง token/password หรืออ้างว่ารายการโปรแกรมเท่ากับการสำรอง configuration ทั้งหมด ข้อเสียคือเหตุการณ์ลง Windows ใหม่ไม่ได้เกิดทุกสัปดาห์

### ProofPack

รวมภาพ บันทึก และไฟล์ของเหตุการณ์ เช่นรับของเสียหายหรือบันทึกสภาพห้อง เป็น timeline และ ZIP สำหรับส่งต่อ [RentCheck](https://www.getrentcheck.com/reporting-data) มีงานเปรียบเทียบ inspection เข้า–ออกอยู่แล้ว จึงต้องเลือกเหตุการณ์แคบ ๆ ให้ต่าง ไม่รับรองว่าภาพหรือเวลาจากแอปมีผลทางกฎหมาย หรือพิสูจน์ได้ว่าไม่เคยถูกแก้

### WatchRules

เตือนเฉพาะรุ่น/ไซซ์/เงื่อนไขสินค้าที่เลือก แต่ [changedetection.io](https://github.com/dgtlmoon/changedetection.io) มีทั้งตรวจราคา restock browser steps และกฎ AI อยู่แล้ว จุดต่างจะต้องเป็นการรองรับแหล่งเฉพาะที่ตรวจได้จริง เริ่มหนึ่งเว็บไซต์ที่อนุญาตการเข้าถึง และเก็บหลักฐานแต่ละ alert ต้นทุนสำคัญคือการดูแล scraper ไม่ใช่ Dashboard

### ReceiptHub

เก็บบิล ใบรับประกัน และวันหมดอายุ แต่ [Warracker](https://github.com/sassanix/warracker) มีเอกสาร reminders และ lifecycle ของการเคลมอยู่แล้ว แนวทั่วไปจึงซ้ำมาก หากจะทำควรเจาะการเตรียมชุดเอกสารสำหรับสินค้า/ร้านประเภทเดียวและมีผู้ใช้ทดสอบจริง

### Screenshot Inbox

[Pixel Screenshots](https://blog.google/products-and-platforms/devices/pixel/google-pixel-screenshots-tips/) มีการสรุปและค้นข้อมูลจากภาพแคปอยู่แล้ว “ใส่ AI แล้วค้นภาพ” จึงไม่ใช่ความต่างเพียงพอ อาจยังเหมาะเป็นโปรเจกต์ส่วนตัวข้ามอุปกรณ์ แต่ต้องทดลอง OCR ภาษาไทยและวิธีนำภาพเข้าระบบก่อน

### Learning Dashboard

เป็นโปรเจกต์ CRUD ที่ดีสำหรับฝึกพื้นฐาน แต่ผู้ใช้ในบทสนทนานี้ไม่ได้มีแรงจูงใจจะจดบันทึกหรือดูสถิติ การเพิ่มฟีเจอร์อาจไม่เปลี่ยนเรื่องนั้น จึงไม่ควรพัฒนาต่อโดยถือว่าผู้ใช้ต้องชอบในภายหลัง

## ข้อเสนอสำหรับรอบถัดไป

ผู้จัดทำเสนอให้เริ่ม **Repo Passport แบบอ่านไฟล์และส่งออกรายงาน** เนื่องจากผูกกับเป้าหมายฝึก GitHub และลอง stack ของผู้ใช้ที่ทราบแล้วได้ตรงที่สุด ยังไม่เสนอให้สร้างเต็มระบบหรือเปลี่ยนโค้ด DevQuest จนกว่าจะมีความสนใจในผลลัพธ์ตัวอย่าง

หากต้องการตัวอย่างที่คนทั่วไปเข้าใจเร็วกว่า ให้ทดลอง **ChangeLens ด้วย CSV สองไฟล์** สิ่งที่เราต้องพิสูจน์คือการสรุปและตรวจความต่างได้ถูกต้อง ไม่ใช่ความสามารถเขียน Dashboard อีกหน้า
